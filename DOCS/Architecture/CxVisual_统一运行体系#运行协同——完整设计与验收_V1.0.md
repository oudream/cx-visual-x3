# CxVisual · 统一运行体系 · 运行协同 — 完整设计与验收（初简版）

> **版本**：V1.0（初简版 / 设计讨论稿）  
> **日期**：2026-10-20  
> **定位**：供后续细化、源码归位、验收设计使用；**不是完整规格，也不代表功能已经实现**。  
> **约束**：沿用 CxVisual 既有 Foundation / Mechanism / Professional 与现有项目布局，原则上不新增项目；保持 MEM 唯一工程真源、MOC 唯一构建桥、MRK 统一运行执行、MDS 统一运行时数据；C# 与 Studio 共用语义。  
> **证据说明**：目前仅参考对 x3 `master` 的定向代码查看和历史规格基线；“建议/待实现”不能写成已验证的源码行为。

## 1. 定位
运行协同负责多执行实例、多个子流程与多个专业能力之间的**事件传递、依赖同步、等待、汇聚和调用关联**。运行协同不拥有 MOL 的控制/事件连接定义，也不实现专业内部具体算法或设备协议。

## 2. 核心能力
| 能力 | 最小约束 |
|---|---|
| 事件触发 | 事件类型、来源、订阅生命周期、去重键与过滤契约 |
| 子流程调用 | 固定 Content 版本、输入输出、调用链、错误向上传播规则 |
| 同步等待 / Join | All / Any / Quorum 等明确完成语义；超时/取消一致 |
| 跨专业协作 | Motion/Vision/Inspection/IoT 通过已注册能力与数据契约沟通 |
| 相关性 | `RunId`、`CorrelationId`、`InvocationPath`、事件序号贯通 |
| 异步与持久等待 | 明确何时需持久 Journal/Recovery，重启可恢复不重复副作用 |

## 3. 贯通场景：X-Ray 检测
1. Motion 完成到位后发出有身份的 `MotionReady` 事件。
2. 同一 SN 的采图步骤等待该事件，启动 X-Ray；其图像经数据端口交给 AI。
3. AI 与传统算法可以并行运行，Inspection 等待 Join 汇聚并统一判定。
4. 将结果交 MES 并等 ACK，ACK 与设备物理完成必须区分；超时按保障策略处理。
5. Trace 显示每个事件/调用的源节点与延迟，失败能定位跨专业边界。

## 4. 边界和不变量
- **工程连线在 MOL、编译在 MOC、投递/等待在 MRK、数据在 MDS**。
- 共享 Content 定义可被多个实例调用，调用位置和运行状态必须隔离；不能用一个全局“当前子流程”变量。
- 至少一次消息投递可能产生重复，因此可能有副作用的动作必须采用去重/幂等方案；不要承诺无前提的恰好一次执行。
- 协同超时不能被吞掉；下游取消/故障应按明确传播策略反馈上游。

## 5. 代码承接与建议契约
主 Owner `Mechanism.Runtime`：优先检查 `MRKRuntimeCoordination`、`MRKExecutionTrigger`、`MRKWorkJoin`；MOC `SourceMap` 保持源定位。建议的消息契约：`EventType + CorrelationId + Origin + OccurredAt + PayloadRef + DeliveryPolicy`（**概念草案**）。

## 6. 验收
- 两个 SN 同时执行，共享子流程被各调用两次：参数、结果、事件和 Trace 不串单。
- Join 的 All/Any 在成功、失败、超时、取消场景均返回一致的终态。
- 事件迟到、重复、乱序和回放均有确定策略；撤销订阅后无回调泄漏。
- 假 MES ACK 超时与真实设备到位信号分别测试；模拟断线后能看到明确的挂起/恢复原因。

## 7. 待细化
按控制流、数据流、长流程、状态机分别写触发与 Join 语义，加入背压与缓冲区界限；不把事件系统建成第二个逻辑定义引擎。
