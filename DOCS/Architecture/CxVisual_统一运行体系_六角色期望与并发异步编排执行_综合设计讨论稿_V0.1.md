## 00. 一页摘要：先用户、后需求、再运行体系

**我们要做的不是“线程池工具包”，也不只是“画流程图的解释器”，而是让软件代码、专业能力、工程编排、调试和生产操作共用一套可信的运行语义。**

~~~text
R1 软件开发者 ──┐
R2 专业开发者 ──┤  提供业务方法、能力与参数
R3 工程编排用户 ─┤  使用同一能力契约、任务结果和执行状态
R4 调试工程师 ───┤
R5 生产操作用户 ─┘
           ↓
    Mechanism.Runtime / Execution
    唯一执行引擎：任务/流程/上下文、业务调度
    异步挂起恢复、并行归并、资源仲裁、诊断
           ↓
    Foundation.Infrastructure / Concurrency
    F19：Worker、Queue、非阻塞等待、Timer
    并发上限、同步、取消、生命周期、基础指标
           ↓
    .NET Framework 4.8 Task / ThreadPool / IO
           ↑
R6 平台维护者：维持两个内聚实现中心及各原Owner
~~~

**核心期望**：
- 软件开发者通常1～3行完成常见提交/调用；不手工造线程、队列、锁。
- 专业开发者一次实现算法、通信或设备Provider，同时支持代码与编排复用。
- 工程用户拖节点、连线并配置执行关系，不必理解Thread、Task或Lock。
- 调试工程师准确看到哪个任务、哪个设备、哪次请求，正在等待什么。
- 操作员知道生产是否安全、故障在哪里、控制动作是否已确认。
- 平台团队只有**一套并发基础 + 一套业务执行引擎**，不按每个专业或节点复制调度器。

### 00.1 讨论共识与待进一步裁决

| 内容 | 当前阶段性状态 | 不应误解为 |
|---|---|---|
| 从R1～R6需求倒推架构 | 认可的设计方法和验收方向 | 全部需求已最终冻结 |
| F19 Concurrency / Runtime Execution 两个集中目录 | 认可的组织方向 | 所有对象类名和文件已经确定 |
| 单一运行语义服务代码和编排 | 认可的设计约束 | 所有简单调用都经完整Flow解释器 |
| 不复制第二套执行引擎 | 认可的架构约束 | 取消Orchestration原有流程定义职责 |
| 工作项、流程实例、上下文、执行组等 | 逻辑模型 | 必须新增同名CLR类 |
| 生命周期、错误、超时、外部状态 | 待落实状态转换表的设计要求 | 当前已实现的工业安全保证 |
| E01～E18 P0/P1 | 初步建设优先级 | 已通过编译或测试 |

## 01. 第一层：六类角色期望

### R1 软件开发者：使用既有体系写业务代码

**他希望做的事**：提交后台工作、串行或并发运行、异步通信、延时/定时、等待结果、请求取消、查看状态。

**希望简单到什么程度**：大多数常见任务1～3行调用；配置少数与业务有关的约束。开发者不需要自行处理Thread、Mutex、Lock、ManualResetEvent、队列唤醒或线程回收。

| 场景 | 开发者只声明 | 体系内部承担 |
|---|---|---|
| 后台运算 | 要执行的Action/Func | 工作提交、异常、执行资源 |
| 按Key串行 | Key和工作 | 同Key排队、跨Key并发 |
| 限制并行 | 最大并发度 | Worker调度、限额与统计 |
| 设备异步请求 | Request、Timeout、Token | 非阻塞等待、应答匹配、超时事件 |
| 队列积压 | 容量和溢出策略 | 接纳/拒绝/淘汰、通知 |
| 周期任务 | Interval及禁止重入策略 | 定时、启停和状态 |
| 工作结束 | Stop或Cancel请求 | 停止接单、排空、资源清理 |
| 诊断 | 查询Handle或Metrics | 阶段、原因、日志与耗时 |

**便捷API期望（仅示意，非实际签名）**：

~~~csharp
worker.Post(() => ProcessImage(image));

Result result = await worker.InvokeAsync(() => Calculate());

await worker.StopAsync();
~~~

**反例**：把一个同步阻塞函数包进Task.Run，只改变它占用哪条线程，不等于实现真正的异步IO；不能为了好看而对用户隐藏这个区别。

### R2 专业能力开发者：写一次专业功能、多处直接复用

包括Vision/CT/Automation/IoT/AI算法、协议、设备SDK或Provider的开发者。

**他希望做的事**：实现专业算法或设备行为，声明输入输出Schema、能力/版本、并发安全、运行位置、资源及取消要求；无需另写一套编排适配的业务算法。

**必须提供的便利**：
- 同步函数、Task异步函数、长任务都能接入统一能力系统。
- 能力的输入输出Schema可供代码调用、参数编辑、节点端口和运行校验共用。
- 可声明不能并发、仅同一会话串行、必须专用线程或特定资源等约束。
- 平台统一承担运行状态、队列、追踪、错误和生命周期。
- 专业Provider继续负责设备协议、外部操作真实完成条件、必要的硬件安全动作。
- 不强制将成熟C++、Go、SDK或AI服务改写为一种语言。

**示意**：开发者实现DetectAsync(Image, Token)，编排端自动将该能力展示为可绑定输入/输出的节点；两种入口最终使用同一专业实现和相同结果含义。

### R3 工程编排用户：用图形操作而不是写并发代码

用户往往精通生产流程但不熟悉Thread、Task或async/await。

| 用户意图 | 界面所需操作 | 平台执行责任 |
|---|---|---|
| A后执行B | 连线 | 校验依赖、条件满足再推进 |
| 传统算法与AI并行 | 并行分支 | 分支调度、上下文隔离 |
| 等AI结果后再继续 | 等待/归并节点 | 异步挂起、恢复、关联 |
| 按产线顺序 | 配置Key=LineId | 同Key顺序、跨Key并发 |
| 积压12张图 | 配置容量和规则 | 可淘汰队列项、失败通知 |
| 异常或超时 | 连接失败/超时路径 | 故障传播、补偿选择 |
| 调用已有流程 | 选择子流程 | 参数/结果/数据作用域 |
| 独占设备 | 选择设备资源 | Runtime权限和资源仲裁 |
| 多个设备/变量 | 连接数据端口和属性 | Schema检查、值传递和生命周期 |

**日常面板只显示**能力、输入输出、必要参数、超时、失败处理。ExecutionGroup、优先级、线程亲和、特殊队列策略等放“高级设置”。默认值应来自能力契约，不能靠系统猜测硬件能否并行。

### R4 工程调试用户：回答“为什么卡住，能否安全介入”

要能直接看到：
- 运行Plan版本、FlowInstanceId、WorkId、ProductId/LineId/DeviceId和CorrelationId。
- 节点是Queued、Running、Waiting、Completed还是Failed；等待的是设备应答、AI结果、Timer、资源还是其他分支。
- 执行组的队列深度、已等待时间、超时阈值、资源持有者。
- 该次执行的输入输出、异常、错误码、专业日志和分支汇合情况。
- 模拟调试、正式运行只读观察和受授权独占调试的权限区别。
- 可用断点/单步只发生在逻辑或专业安全点；不能随意挂起正在做危险动作的线程。

**期望不是“节点染色”而已，而是按流程实例可解释、可定位、可审计。**

### R5 运行操作用户：安全启停、异常清楚

操作员不需要理解并发内部概念。需要：
- 启动前置条件/设备状态清晰；不能启动时给出原因。
- 安全停止是否已确认，不把“停止请求已发送”冒充“硬件停止”。
- 看出是采图积压、通信断线、AI不可达、算法故障还是资源等待。
- 淘汰图像、漏检风险、检测失败必须呈现明确业务结果。
- 发生设备命令超时，显示“结果未确认”及允许的处置。
- 在线发布新工程需要安全切换，失败不让正在生产的Plan半修改。

### R6 平台开发维护者：集中、内聚、可测试

需要：只维护一个F19并发基础目录和一个Runtime执行目录；同一执行语义与状态模型被代码、Studio和专业Provider复用；不强迫每个子方面单独线程或Manager；尽量复用.NET Framework 4.8原生Task/ThreadPool/CancellationToken/SemaphoreSlim。

**集中的是执行实现，不是把所有专业能力、协议、图形和编排定义全部塞进一份“大Runtime”。**

## 02. 第二层：易用性等级和统一使用入口

| 等级 | C#代码开发者 | Studio编排用户 | 希望覆盖 |
|---|---|---|---|
| L0 无感 | 只写业务函数，由能力约束决定运行方式 | 普通节点连线 | 基本顺序场景 |
| L1 一行 | Post、InvokeAsync、DelayAsync | 并行、等待、分支 | 常见并发/异步 |
| L2 少量配置 | 并发度、容量、Key、超时 | 节点面板配置 | 大部分实际工业场景 |
| L3 高级 | ExecutionGroup、资源、亲和与诊断 | 高级编排和受控调试 | 复杂性能与设备需求 |
| L4 底层 | Queue、Signal、Gate等基础组件 | 自定义专业能力/策略 | 少数特例 |

**设计指标（非已达到事实）**：常用操作约1～3行代码；争取80%～90%工程编排在L0～L2解决。不能以省略安全策略、数据所有权或设备结果确认来实现“简化”。

### 02.1 三种入口，共用一套语义

1. **代码便捷入口**：普通业务开发直接调用F19 Worker或专业Async接口。
2. **Runtime统一入口**：需要标准执行身份、状态、配额、资源和诊断的任务，经业务执行入口提交。
3. **图形编排入口**：Studio将流程定义编译为Plan，由Runtime执行；节点与代码使用同一专业能力。

统一状态与结果不等于“每个Post都必须先创建一个完整流程图”，也不等于“图形节点要有另一套Task/Result实现”。

## 04. 第四层：执行体系的五个核心逻辑模型

| 模型 | 它代表什么 | 它不是什么 |
|---|---|---|
| **Execution Plan** | 编译、校验、引用已解析的不可变执行定义 | 一个正在跑的线程或任务 |
| **Flow Instance** | 一个产品/批次/请求的一次完整流程执行 | 一份新的永久流程定义 |
| **Work Item** | 一次可被调度、等待或完成的具体工作 | 物理线程 |
| **Execution Context** | 本次执行的身份、数据、作用域和取消/追踪上下文 | 随处可写的全局Map |
| **Execution Group** | 一组任务共享的串行、并发、排队策略 | 必定独占一条线程 |

补充必须区分的对象/语义：
- **Runtime Session**：长期运行的工作站/设备/协议会话；可以承载很多Flow和Work。
- **Resource Lease**：设备、SDK、GPU或数据生命周期的占用凭证。
- **External Operation**：一次实际外部设备/服务操作，可能已有副作用，与本地等待完成结果不是一回事。
- **Capability/Provider**：专业能力声明与实际实现，运行引擎不复制其专业逻辑。

以上是逻辑模型，不意味着必须新建完全同名的五个类。具体类型需与V6.4、V7.8、新主仓现有类型逐项查重。

### 04.1 身份与关联

~~~text
PlanId + PlanRevision
    └── FlowInstanceId + BusinessKey（产线/产品/设备/批次）
          ├── WorkId / NodeInstanceId
          ├── ExecutionContext / ParentContext
          ├── ExecutionGroupKey
          └── CorrelationId / CausationId
                 └── 外部Provider：SessionId / OperationId / ResourceLeaseId
~~~

身份必须具有明确作用域；跨分支/跨进程应答不得只依赖“最近一次结果”推断归属。

## 05. 第五层：统一生命周期与状态分离

### 05.1 主任务生命周期

~~~text
Created
   ├── AdmissionRejected（未接纳）
   └── Accepted → Queued → Running ───────────────────┐
                            │     ↑                  │
                            ↓     │                  ↓
                          Waiting ┘              Completed
                                                   /  |  \
                                             Failed Cancelled TimedOut*
~~~

注：此图只是核心状态关系，不是完整合法转换表。已接纳且允许丢弃的排队任务另有明确Dropped结果。CancelRequested/PauseRequested是请求与过渡事实，不直接等于已取消/已暂停；某些失败可从多个非终态触发。

### 05.2 需要分开维护的四种状态

| 状态对象 | 关注什么 | 不能混淆 |
|---|---|---|
| Submission/Admission | 提交是否接受、拒绝、已淘汰 | 已接纳 ≠ 已开始 |
| Work Item | 排队、执行、异步等待、结束 | Waiting ≠ 工作线程一直阻塞 |
| Flow Instance | 整个流程和所有必要分支进度 | 某节点完成 ≠ 整体完成 |
| External Operation | 外部命令已发送、接受、执行、确认、未知 | 本地超时 ≠ 设备未执行 |

**重要状态原则**：TimedOut可指调用方等待截止；与此同时外部设备Operation仍可能Running或Unknown。不能以一个Bool成功/失败覆盖两者。CancelRequested不意味着操作已经安全停止。

### 05.3 会话、数据与资源生命周期还应独立

一个AI调用超时后，主流程可能转入失败分支，但AI服务中的推理任务未必被停止，图像引用和外部请求记录也不能立即无条件销毁。需要安全释放和迟到结果处理策略。

CT扫描时更加明显：停止请求只意味着进入停止过程，真正释放运动控制和X-Ray资源必须以专业/硬件的安全确认作依据。

## 06. 第六层：并发、异步、队列与调度是正交维度

不建议用一个大枚举混合“同步/异步/串行/并行/优先级/资源”。建议以多个可组合维度表达：

| 维度 | 可选/候选语义 | 默认约束 |
|---|---|---|
| 执行位置 | Inline、SharedPool、Dedicated、ExternalService | 不能以线程变化冒充IO异步 |
| 并发度 | Serial、Parallel、MaxConcurrency、KeyedSerial | 遵守Provider线程安全声明 |
| 队列 | Capacity、FIFO、Priority、Backpressure | 无静默丢弃，无隐式无界积压 |
| 等待 | Task/IO、Event/Response、Timer、Join | 等待时不占不必要的工作线程 |
| 串行范围 | WholeFlow、SpecificStage、Resource | 同Key占位 ≠ 一直持有线程 |
| 资源 | Exclusive/Shared、GPU、设备、内存预算 | 正式设备Runtime仲裁 |
| 错误 | Fail、RetryIfSafe、Compensate、Manual | 非幂等硬件动作默认不自动重试 |
| 诊断 | Metrics、Trace、Snapshot、Debug | 不拖慢关键IO路径 |

### 06.1 ExecutionGroup 的三种业务串行范围

**整流程串行**：Line1前一个产品全部检测完才处理后一个；最简单，但可能降低UPH。

**阶段串行**：同一Line的PLC/采图阶段排队，算法和AI任务可并行重叠；对高吞吐Vision往往更实用。

**资源串行**：只对同一探测器、运动控制卡或不可重入SDK限制；适合复杂设备。

必须由能力约束和工程配置共同决定串行范围，**不可默认用一个全局Lock锁住整张编排图**。

### 06.2 异步等待不占线程，但可能占逻辑顺序

PLC同一会话通常要求请求按规定次序发送。等待应答时释放Worker线程，不意味着下一个请求可以违反会话顺序提前发送。协议Session仍可保留逻辑执行槽位或请求序列占用。

~~~text
提交PLC请求
 → 先建立Correlation/应答匹配登记
 → 发送到Channel
 → 本地Work进入Waiting（不占用Worker线程）
 → IO收应答 → Protocol匹配
 → 完成本次异步等待 → Runtime推进后续
~~~

不能把IO线程变成设备业务计算线程；不能在持锁时调用可能阻塞的外部回调或无界发送。

### 06.3 背压/丢弃的基本安全规则

可以淘汰的是**已经接纳、尚未执行、且被业务明确标注为可淘汰**的队列工作。不能把已经执行的CT扫描或结果未知的PLC控制指令作为普通DropOldest队列项。

被淘汰的图像工作必须产出明确记录与对应产品的业务失败事实；不仅是队列计数减一。还需考虑图像数据的字节容量，不能只按任务数量估算内存负担。

## 07. 第七层：数据、并行分支、等待与归并

### 07.1 数据语义

- 每个Flow拥有独立执行上下文。
- 并行分支默认使用不可变快照或生命周期受控的只读数据引用。
- 分支有独立局部结果；跨分支写共享数据需显式声明一致性/冲突策略。
- 图像、CT体数据尽量避免不必要的大规模复制，但要明确原始Buffer何时安全可复用。
- 每次AI结果通过FlowId/BranchId/CorrelationId匹配到正确产品。
- 主流程转失败分支后，迟到结果不能写回一个已结束/已切换版本的流程。

### 07.2 四类归并策略与必须说明的尾部行为

| Join模式 | 开发者表达 | 平台还必须规定 |
|---|---|---|
| WaitAll | 等全部分支结束 | 某个失败后是否提前失败或继续等待 |
| WaitAny | 任一分支结束 | 其他分支取消、继续还是转后台 |
| FirstSuccess | 采用第一个成功结果 | 全失败如何返回；其余如何清理 |
| ConditionalJoin | 满足条件才推进 | 条件所需的数据、超时、重复事件 |

**真正的问题**不是Join节点能不能画出来，而是**合并后剩余任务、外部操作和数据引用如何处置**。这必须成为执行引擎的标准语义。

## 08. 第八层：C#与编排用户使用同一运行体系

### 08.1 期望的少量C#调用入口（仅体验示意）

~~~csharp
// 便捷：普通业务工作
worker.Post(() => ProcessImage(image));

// 设备异步：由协议/Provider负责应答匹配
PlcResult plc = await provider.RequestAsync(request, cancellationToken);

// 需要统一运行追踪/资源控制时
ExecutionHandle job = engine.Submit(work, options);
ExecutionResult result = await job.WaitAsync();

// 完整流程执行
ExecutionHandle flow = engine.StartFlow(plan, inputs, options);
flow.RequestCancel();
ExecutionSnapshot state = flow.GetSnapshot();
~~~

**名称只是便于讨论的API草案**，不是批准新增ExecutionHandle等类。既有类型满足时应复用或适度调整，不按示例创建空壳类。

### 08.2 同一个运行行为的两种入口

| SDK动作 | 编排界面动作 | 必须统一的行为 |
|---|---|---|
| Submit | 触发能力节点 | WorkId、接纳结果、状态 |
| StartFlow | 启动主/子流程 | FlowId、Plan版本与作用域 |
| WaitAsync | 等事件/应答/分支 | 关联、超时、异步挂起 |
| RequestCancel | 取消任务/流程 | 请求不冒充确认停止 |
| GetSnapshot | 运行图高亮与诊断 | 同一个快照和Trace |

Studio默认不暴露Thread、锁和细节；高级模式才显示ExecutionGroup、队列、优先级、资源和线程亲和。模拟、只读观察、授权调试三种模式必须在界面明确区分。

## 10. 第十层：三种主进程与正式运行隔离

| 职责 | Studio编排进程 | Runtime.Host生产进程 | AI服务进程 |
|---|---|---|---|
| 定义与草案 | 工程编辑、模型、模拟、编译请求 | 读取已发布Plan | 使用契约与模型版本 |
| 引擎实例 | 编辑/模拟/观察上下文 | 正式运行上下文 | AI任务和推理上下文 |
| 现场设备 | 不同时持有生产控制会话 | 正式Device Session、独占租约 | 默认不控制生产硬件 |
| 运行事实 | 展示实时快照、诊断和日志 | 产生权威事实与审计 | 返回推理状态与结果 |
| 内部总线 | Studio自己的Bus/终端模块实例 | Runtime自己的Bus/终端模块实例 | 按消息契约通信 |
| 正式变更 | Draft→Validate→Compile→授权申请 | Safe Publish/Reject、版本切换 | 版本协同与能力变更 |

不因此新增独立Bus、Monitor、Daemon或Terminal主进程。旧ccxx、device_communicator、gcl3的成熟代码提供运行行为和监控经验，但不直接照抄其历史进程拓扑。

**安全要求**：真实物理联锁、运动控制卡时序、X-Ray安全动作必须由相应设备控制体系保障；软件运行租约不是物理安全联锁的替代品。

## 11. 用四个专业案例压力测试整套设计

### CASE-VISION-01 双产线Vision：高吞吐、算法并行与结果归并

~~~text
产品/PLC数据、采图完成
  → LineId关联和阶段串行（容量示例：12张，按业务实际规则）
  → 传统算法与AI任务并行
  → WaitAll或明确的合并策略
  → 后处理、判定、MES/PLC反馈
~~~

必须通过：
1. 同一Line在受约束阶段有序，Line1/Line2能并发。
2. AI迟到结果不会被误用为下一个产品的检测结果。
3. 队列积压淘汰必须有失败结果、原因、统计。
4. 图像Buffer在仍被传统算法或AI使用时不得释放。
5. 代码开发者无需再自己建两套Queue/线程；编排者无需自行写Lock/WhenAll。

### CASE-IOT-01 PLC/IoT：多通信会话与异步请求应答

~~~text
Channel IO → Protocol解码/关联 → 测点更新/事件发布
                         ↑
  Request → 登记操作 → 发送 → 非阻塞Waiting → 应答/超时
~~~

必须通过：先登记后发送避免快速应答竞态；同一会话保持协议顺序；多个Session可并发；断线/重连可观察；命令超时不自动被解释为设备未执行；非幂等控制不可默认自动重发。

### CASE-CT-01 CT扫描与重建：资源互斥、长任务和数据寿命

~~~text
设备独占与安全检查 → 运动/触发采图
 → 体数据交接（受控引用）
 → 重建（CPU/GPU长任务）
 → 3D/检测/结果管理 → 确认资源释放
~~~

必须通过：Studio不与Runtime同时控制真实设备；停止/取消不能绕过控制卡的安全停止；GPU长任务可查询进度；重建阶段不会阻塞硬实时采图触发；数据引用安全、Plan版本可追溯。

### CASE-AI-01 跨进程推理：队列、异步返回与故障

必须通过：有真实的请求ID、超时和远程状态；跨进程失败不被当成本地Task异常的唯一语义；GPU队列深度和已等待时间可观察；迟到结果不能覆盖已关闭产品；能力实现同时可被代码和编排调用。

## 12. 必须遵守的公共默认行为

| 事项 | 建议默认 | 禁止默认 |
|---|---|---|
| 并发安全未知 | 保守串行或要求能力声明 | 擅自并发写设备/SDK |
| 队列满 | 返回拒绝或有界背压 | 静默丢任务或无界堆积 |
| 异步异常 | 进入Result/Trace | Fire-and-forget无声失败 |
| 超时 | 说明本地等待截止，外部状态另记 | 判定设备未执行 |
| 取消 | 协作取消、等待安全结果 | 随意强制终止工作线程 |
| 非幂等控制 | 默认不自动重试 | 无限制重发设备写指令 |
| 并行数据 | 只读共享/分支局部结果 | 无同步共享写、提前释放 |
| 在线编辑 | RunningPlan与草稿隔离 | 草稿直接改生产执行 |
| 设备访问 | Runtime权威租约和专业联锁 | Studio绕过授权控制设备 |
| 诊断 | Work/Flow/Plan/Correlation与耗时 | 只返回Boolean状态 |

这些是要贯彻到开发和验收的**行为约束**，比预先确定几十个类名更重要。

### 附录A：简明术语

| 术语 | 简明定义 |
|---|---|
| Concurrency 并发 | 多个工作在时间上交错推进，不意味着同时占CPU |
| Parallelism 并行 | 多个工作真正同时执行 |
| Asynchrony 异步 | 等外部事件/IO完成时不必阻塞工作线程 |
| Orchestration 编排 | 组织依赖、条件、并行、等待、子流程和故障路径 |
| Work Item | 一次可排队、运行、等待、结束的工作，不是线程 |
| Flow Instance | 一次业务流程执行，包含多个Work |
| Execution Group | 约束一组任务的执行顺序、并发度与队列 |
| Operation | 可能发生外部副作用的设备或服务操作 |
| Join | 多分支满足规则后合并结果和推进 |
| Lease | 资源、设备或数据使用权/生命周期凭证 |

**整份设计的评价标准**：不是平台新增多少类，而是用户代码更少、编排更直观、调试更高效、生产运行更可信、真实故障可验证、两个核心目录长期易维护。
