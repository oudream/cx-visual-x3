# ccxx深入分析 02：Describe / Profile / Context 元数据与配置

> 源码固定基线：[`26cecfb02e861ce6b821b33350493bac4793e997`](https://github.com/oudream/ccxx/commit/26cecfb02e861ce6b821b33350493bac4793e997)；2026-10-14静态审计。与当前C#的CxNode**结构和所有权不同**，只按功能复用。
> 对应：`Foundation.Data`、`Mechanism.Core`、`Mechanism.Data`，三个项目当前在x3中Core有样例树，Data机制为骨架。

## 1. 抽象结构：不是单纯INI读写

```text
CxIGetSkv / CxISetSkv
        │对象对键值读写的统一接口
        ▼
CxSkv (内存中的 section -> entry -> string 表)
        ▼
CxSkverBase : CxSkv  （loadImpl/saveImpl模板方法）
        ├─ CxSkverIni / CxSkverTxt
        ├─ CxSkverJson  -> CxRapidJson::loadTable/saveTable
        └─ CxSkverXml   -> TinyXML 普通Config / xml_4level
        ▲
CxSkverFactoryManager（后缀工厂）
CxSkverManager.beginUse / endUse（共享引用/延迟保存管理）

CxDescribeBase（基本属性类型及约束）
  └─ CxDescribeUnit （一组属性描述）
         └─ CxDescribeCatalog（多Unit及数据映射）
               └─ CxDescribeProject（多Catalog的描述项目）
                 （这些“Project/Catalog/Unit”是旧元数据描述体系）
```

源证：[`cxcontext.h`](https://github.com/oudream/ccxx/blob/26cecfb02e861ce6b821b33350493bac4793e997/ccxx/cxcontext.h)、[`cxprofile.h`](https://github.com/oudream/ccxx/blob/26cecfb02e861ce6b821b33350493bac4793e997/ccxx/cxprofile.h)、[`cxdescribe.h`](https://github.com/oudream/ccxx/blob/26cecfb02e861ce6b821b33350493bac4793e997/ccxx/cxdescribe.h)、[`cxprofile.cpp#L431-L592`](https://github.com/oudream/ccxx/blob/26cecfb02e861ce6b821b33350493bac4793e997/ccxx/cxprofile.cpp#L431-L592)、[`cxdescribe.cpp#L759-L1014`](https://github.com/oudream/ccxx/blob/26cecfb02e861ce6b821b33350493bac4793e997/ccxx/cxdescribe.cpp#L759-L1014)。

## 2. 真实API行为

- `CxIGetSkv`分别提供section级和entry级`getValue/hasEntry/hasSection`；`CxISetSkv`提供`setValue`。枚举类型转换及缺省值行为由实现决定。
- `CxSkverBase::load(path)`先判断文件存在，执行`loadImpl`成功后记录FilePath/Name/Suffix/Dir；`save(path)`选显式路径、加载过的路径或默认保存路径，并建立父目录。
- `CxSkverManager::beginUse`根据文件后缀工厂创建对象、可选加载、增加引用计数；`endUse(profile, save)`减少引用并在最后一位使用者退出时按`useSaveCount`保存、删除对象。
- `CxSkverJson::loadImpl`调用`CxRapidJson::loadTable`，以`sectionEntryValues.size()>0`作为成功；`CxSkverXml`按普通`root/config`或`xml_4level`处理。
- `CxDescribeManager::loadProject`读取Self目录信息及多个Catalog；`loadCatalog`读取Unit关联的数据位置/重写标记；`loadUnit`通过类型描述工厂实例化具体属性描述。
- `CxDescribeBase`包含类型ID、名称/标题、只读、可见、非空、正则、上下限、枚举值、外键、默认值等描述能力；`CxDescribeUnit`聚合属性、`CxDescribeCatalog`组织Unit、`CxDescribeProject`组织Catalog。原格式允许大量表驱动页面和对象属性定义。

## 3. 与CxVisual的唯一Owner边界

| 旧能力 | 新项目应承接的概念 | 不应直接搬迁的部分 |
|---|---|---|
| SKV值读写、JSON/XML/INI适配 | `Foundation.Data` 的编码、序列化、格式Reader/Writer | 对某个CxProject的业务解释/持久化事务 |
| Describe属性定义、约束 | `Mechanism.Core` 的PropertyDefinition / Metadata / Validation（候选角色，类型名按规格决定） | 第二套`CxDescribeProject`成为工程权威 |
| Catalog/Unit与外部数据映射 | `Mechanism.Data` 变量/Binding及公共资源定位 | 混入UI窗口/工作台专有状态 |
| Configure读取生命周期 | `Mechanism.Lifecycle`配置迁移，`Runtime.Host`加载流程 | 让全局`CxSkverManager`替代项目Revision/事务 |
| 属性编辑器映射 | `Mechanism.Visual`或`Presentation.Wpf`展示适配 | 旧Descriptor直接持有WPF控件 |

关键：**旧`CxDescribeProject` ≠ 新`CxProjectDocument/CxNode`**；需要建立一条“旧描述格式→新PropertyDefinition/资源”的明确迁移Adapter，而不是简单同名合并。

## 5. 先选三组Golden兼容文件做测试

1. INI/JSON/XML：读→修改字段→保存→重新加载；验证Unicode、缺省字段、未知字段保留、空Section、错误文件和部分写入恢复。
2. Describe Project→Catalog→Unit→typed fields：读取真实旧工程描述，检查属性顺序、类型、默认值、上下限、依赖关系；老格式与新工程定义间验证ID稳定及序列化差异。
3. 同一配置被两处使用：`beginUse/beginUse/endUse/endUse`，分别测试save=false/true、错误路径、并发访问与最后引用释放。

## 6. 最终开发产出（后续项目逐项批准）

- `Foundation.Data`：纯格式适配、不依赖CxNode；
- `Mechanism.Core`：唯一属性元数据定义、类型Id及约束；
- `Mechanism.Data`：与外部变量/数据资源的Binding，独立于配置序列化；
- 兼容导入/导出：Old SKV/Describe -> New Definitions（带版本、预览差异、回滚与审计）。
