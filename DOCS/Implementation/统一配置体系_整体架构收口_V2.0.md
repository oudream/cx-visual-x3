# CxVisual 统一配置架构收口 · 核心契约和运行机制 V2.0

> 依据：《CxVisual_统一配置体系_双项目架构_完整API与案例审查_V1.3.md》。
> 本文区分：目标架构、已实现/已验证、未实现。禁止把类型数量视为功能完成率。
> 已定项目位置：Foundation/Data/Configuration 与 Mechanism/Data/Configuration，各一处，不新增第三套配置项目。
> 现阶段先建设公共配置底座，不将既有机台升级、专业设备或 Studio UI 纳入基础完备性的定义。

## 1. 统一对象关系（不得另起配置对象树）

\`\`\`text
FCMConfigSchema（Definition，按SectionId注册）
   ├─ FCMConfigMemberDescriptor（类型/MemberId/Order/规则/生效策略）
   └─ FCMConfigDependencyGraph（字段和截面依赖）

FCMConfigIdentity（SectionId + ScopeKind + ScopeId）
   └─ MHSConfigSection<T>（唯一实例真源，不是第二个Schema）
        ├─ MHSConfigEdit<T> / FCMConfigChangeSet（候选和变更）
        ├─ MHSConfigStorage（版本、文件、审计）
        ├─ MHSConfigSnapshot<T>（固定读视图）
        ├─ MHSConfigApplyReview<T> / Decision / Result（受控生效）
        └─ MNMConfigChangePublisher<T>（提交/生效事件）

MVBConfigLayeredProfile<T>（组合现有实例的显式覆盖）
   ├─ MVBConfigResolved<T>（一次确定的合成视图）
   └─ FCMConfigRevisionVector（来自实际选中的有效修订）
\`\`\`

**一条真源**：Definition 不是实例数据，层级覆盖并不是第二个 ConfigManager，ConfigDocument 是存储 Token 形态而不是工程对象树。版本的 SchemaVersion / Saved / Effective / Pinned 严格分离。

## 2. 关键不变量（所有实现和测试须共同维持）

1. 配置实例的身份完全由 SectionId + ScopeKind + ScopeId 组成；允许冒号、点号、下划线等字符，不允许字符串拼接导致同名实例碰撞。
2. \`FCMConfigRevisionVector\` 是带实例身份的版本集合，元素顺序与调用时传入顺序无关；重复实例拒绝。它标识一次解析结果，不代表跨文件事务。
3. \`FCMConfigValueState<T>\` 使用 Presence 区分 Missing、ExplicitNull、Defaulted、Present、Invalid；任何版本历史缺失都不能被静默转换为默认值。
4. \`FCMConfigChangeSet\` 按稳定字段路径描述一次草稿或提交修改；当字段不存在和显式 JSON null 时，OldJson/NewJson 的 null（缺失）和 "null"（显式 null）含义不同。
5. 包括 Immediate 在内的所有生效策略都经过 **同一个** Validate → Guard → Revision Compare → Durable Effective Marker → Snapshot Swap → Notify；Commit 只修改保存修订。已注册的必需 Guard 不能被临时 null 参数绕过。
6. 同一任务固定快照不可被后续保存或其他任务生效覆盖，客户端修改副本不会修改真源。
7. 跨层读取固定有效修订向量，并在合成前后双重核验。**这不等于跨多文件的原子提交/发布**，其真正原子语义须另实现。
8. 外部订阅者不能反向破坏已完成的保存或生效事务；异常与慢消费应有独立策略与可靠诊断。
9. 模块只依赖 Foundation→Mechanism 单向，专业配置不向 Foundation 注入 SDK。所有新增 C# 类遵守 FCM/MHS/MVB/MNM 前缀。

## 4. 验收 Gate 的阶段划分

- **基础阶段必须闭环**：A 定义/身份/类型，B 校验和依赖，C 值/历史/版本语义，E 单实例事务与订阅，F 单机受控生效与固定任务快照；失败必须具备明确错误码。
- **当前目标仍需继续建设**：结构化变更与 Undo/Redo、跨实例/跨层原子批量事务、事件序号和重放、统一诊断/访问策略、跨进程持久化消息与恢复故障注入。未达到测试门禁时不标为通过。
- **独立专业阶段再验收**：设备联锁/Readback、Studio 可视化交互、不同格式旧文件迁移、跨机发布和网络故障治理。不得把它们替换为字符串“已完成”。
- **测试类型**：编译 / 基础单元 / 行为集成 / 故障注入 / 并发性能 / 多进程 / GUI / 实机必须分开打勾。

## 5. 开发者应当感知的 API

\`\`\`csharp
FCMConfigIdentity id = new FCMConfigIdentity("My.Section", "machine", "Machine-A");
MHSConfigSection<MyConfig> cfg = service.Open<MyConfig>(id);
var trace = cfg.ExplainState(x => x.Threshold);
FCMConfigRevision version = cfg.Revision;
using (MHSConfigEdit<MyConfig> edit = cfg.BeginEdit("优化采图参数"))
{
    edit.WorkingCopy.Threshold = 120;
    FCMConfigChangeSet changes = edit.Preview().ChangeSet;
    await edit.CommitAsync(cancellationToken);
}
cfg.ConfigureApplyGuard(review => condition
    ? MHSConfigApplyDecision.Allow()
    : MHSConfigApplyDecision.Deny("INTERLOCK", "条件不满足"));
var applied = cfg.TryApplyPendingAtBoundary(FCMConfigApplyPolicy.NextTask, null);
using (MHSConfigSnapshot<MyConfig> pin = cfg.CaptureForTask("Scan-001")) { /* 版本固定 */ }
\`\`\`

此代码用于说明公开用法；\`MyConfig\`、\`condition\`、\`cancellationToken\` 为开发者自己定义的变量。安全 Guard 应在开始编辑和提交前由宿主配置。

## 6. 下一阶段不能再跳过的实现

- 统一版本治理：多 Scope ChangeSet/Txn 协调器应具有原子性定义（一个聚合持久化单元或完整 Journal），不能逐次保存多个文件后宣称原子。
- 通知治理：EventJournal/SubscriptionCursor/事件顺序/异常和慢消费者策略；读写 IO/事件分发边界明确。
- 校验和引用治理：依赖图驱动增量校验、跨 Section 引用解析、环检查、无效目标和资源缺失诊断。
- 配置使用体验：Schema Catalog → 编辑树/视图模型 → 预览 → Undo/Redo → 诊断；通用底座构建 EditorModel，不要求现阶段实际做 Studio 窗口。
- 安全与稳定性：统一敏感字段遮盖策略、审批记录、写崩溃恢复、长期历史保留/压缩、支持的 Provider 能力与失败降级。

本基线是**架构收口与待实现清单**，不是宣告 V1.3 的 24 项、12 个案例和 Gate A～F 已全部完成。必须以 CI/运行证据为准。


## 7. Foundation/Mechanism 双项目内的通用编辑模型

现在 Schema 的依赖不再只存在手写字符串图：\`[FCMConfigDependsOn("ExposureMs")]\` 会通过 \`FCMConfigCatalog.BuildDependencyGraph<T>()\` 构建、验证并支持变更影响分析。未知路径与依赖环是显式错误。

\`MHSConfigEditorModel<T>\` 是完全无 UI 的通用配置编辑会话：\`Draft\` 返回隔离副本，\`Modify(Action<T>)\` 产生历史检查点，\`Undo()/Redo()\` 管理草稿分支；\`DescribeFields()\` 合并 Schema/草稿/保存/生效/错误；\`PreviewAsync/CommitAsync\` 不另建验证或持久化管线，仍通过 \`MHSConfigEdit<T>\` 的事务。

公开用法：

\`\`\`csharp
using (var editor = new MHSConfigEditorModel<MyConfig>(cfg, "调整采图"))
{
    editor.Modify(x => x.ExposureMs = 120);
    var changed = editor.Preview().ChangeSet;
    var impacts = editor.AffectedBy("ExposureMs");
    var fields = editor.DescribeFields();
    if (editor.CanUndo) editor.Undo();
    editor.Redo();
    await editor.CommitAsync(cancellationToken);
}
\`\`\`

Studio 只需将这些对象投影成树/表单，并处理 UI 交互；不再自己实现 Undo/Redo、校验、Diff 或配置存储。外部动态集合成员仍需后续专门的集合编辑器契约与错误边界。


## 8. 配置诊断从零散查询统一到状态模型

\`MHSConfigSection<T>.GetStatus()\` 在一个实例状态锁内生成 \`MHSConfigStatus\`：Identity、Schema、Revision、PendingChanges、保存/生效验证、审计完整性及历史数。审计损坏要产生可机器识别的 Issue，而不是被吞掉。

\`MVBConfigLayeredProfile<T>.GetStatus()\` 组合当前有效版本向量与每层状态。该状态为检查与编辑用途，不应在工业硬实时线程里反复做历史 IO。

\`\`\`csharp
MHSConfigStatus health = cfg.GetStatus();
if (health.HasPending) Examine(health.PendingChanges);
if (!health.IsHealthy) Display(health.IntegrityIssues);
MVBConfigCompositeStatus<MyConfig> composite = layers.GetStatus();
\`\`\`

注意这仍然不是面向网络/跨进程的可靠发布、订阅重放或自动审批。保留明确的未实现边界；不要凭此宣告原文 Gate A～F 全通过。


## 9. 本地变化事件语义

\`FCMConfigChange<T>\` 增加 \`Sequence\` 和 \`TimestampUtc\`。\`MNMConfigChangePublisher<T>\` 为每个实例维护有序事件队列，同步投递时的重入通知只入队不嵌套执行。异常订阅者被隔离，不取消其他订阅的回调。

同一次立即提交产生的 Committed/Effective 共享事务 ID；若订阅者在提交回调内又提交了新修订，原提交不能错误地立即生效较新的修订。事件序号仅在本进程、本配置实例生命周期内递增，不等于持久跨进程游标；持久 EventJournal、可重放订阅、慢消费者背压和跨进程顺序仍属未完成项。
