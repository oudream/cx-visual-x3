> **版本**：V1.0（初简版 / 设计讨论稿）

> **定位**：供后续细化、源码归位、验收设计使用；**不是完整规格，也不代表功能已经实现**。  
> **约束**：沿用 CxVisual 既有 Foundation / Mechanism / Professional 与现有项目布局，原则上不新增项目；保持 MEM 唯一工程真源、MOC 唯一构建桥、MRK 统一运行执行、MDS 统一运行时数据；C# 与 Studio 共用语义。

## 1. 定位
任务调度回答：**哪个运行任务先执行、何时执行、使用哪些有限资源、允许多少任务并发**。它不解释业务流程连线，不做 AI/PLC 的具体业务，也不取代 Foundation 的低级 Worker/线程池。

## 2. 最小能力清单
| 领域 | 最小能力 | 约束 |
|---|---|---|
| 入队 | 任务提交、去重键、取消排队 | 入队成功不代表已经开始执行 |
| 排序 | 优先级、FIFO、公平性、等待时间 | 防长期饥饿，策略显式化 |
| 并发 | 全局/流程/资源池并发上限 | 支持 GPU、相机、重建工作槽 |
| 定时 | 延迟、定时、截止时间 | 使用抽象时钟并考虑时钟漂移 |
| 资源 | Lease/Permit、容量、互斥、释放 | 失败/取消后必须清理 |
| 背压 | 排队容量、拒绝、降载、限流 | 避免 X-Ray 高吞吐压垮 GPU |
| 观察 | QueueDepth、等待时间、运行数量 | 数据进入诊断，不独立建监控真源 |

## 3. 示例：10 个 SN，AI 并发上限 2
10 个产品提交检测任务，控制流各自独立；统一调度器限制 `AI_GPU` 资源池最大并发为 2。其余任务处于排队或等待资源状态。某个任务 AI 完成后释放许可，下一项获得执行机会。**优先级不改变业务步骤之间的依赖顺序**。

调度决策只负责资源和运行时序；MRK 流程执行器仍负责判断“采图完成后才能 AI 检测”。

## 4. 建议契约（概念）
- `Submit(task, schedulePolicy, resourceRequirements)` → 可查询的 TaskId。
- `Acquire(resourceKey, units, cancellation)` → 唯一可释放的 Lease。
- `GetQueueSnapshot()`、`CancelQueued(taskId)`、`OnCapacityChanged(...)`。
- 策略显式包含 `Priority/Fairness/MaxConcurrency/Timeout/Overflow`，定案后与 MRK 现有策略类型对齐。

## 5. 项目与依赖
主 Owner `CxVisual.Mechanism.Runtime`，复用 `MRKExecutionGroups`、`MRKWorkJoin`、`MRKRuntimeCoordination`、`MRKResourceLeaseCoordinator`（以实际代码契约为准）。`Foundation.Infrastructure` 的 `FCRWorker` 提供通用并发原语，不承担工程运行身份和公平调度策略。

## 6. 验收与反例
- 10 个任务、2 个 GPU 许可：任意时刻运行中的 AI 任务 ≤2，所有正常任务最终完成。
- 高优先级插队与低优先级饥饿控制可复现；不允许无上限排队。
- 等待租约时取消，任务不执行且资源计数恢复；任务崩溃时无许可泄漏。
- A 任务超时不应误取消 B；队列拒绝必须返回可诊断错误而不是静默丢单。
- 用仿真时钟测试定时；用并发压力测试抢占/竞态，不把顺序单测当压力测试。

## 7. 待细化
统一 Task/Work/FlowId 概念、资源分类与多资源死锁策略、分布式调度是否需要及相应阶段门槛，**现阶段不先造分布式中间件**。
